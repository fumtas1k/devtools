## 重複・統合メモ

- **Cron**: A-3 で DevOps/Backend の両視点を統合（7フィールド・複数方言・JST・夏時間対応を全部入れ）
- **SSL/TLS証明書**: S-2 に証明書解析＋鍵フォーマット変換（PEM/DER/JWK）を統合 → 鍵変換は ✅ #645 (`key-converter`) として分離実装済み
- **型スキーマ変換**: C-5 に統合（JSON Schema⇄TS⇄Zodに絞ると難度High化）

## 重複・統合メモ（第2回）

- **マスキング系の統合**: S2-1（非構造化テキスト/ログ）と S2-3（CSV 等の構造化データ）は検出正規表現・ダミー値辞書を共有できる。実装時は共通基盤（検出ルールセット＋一貫トークン化）を `src/utils/` に切り出してから 2 本に分けるのが効率的。C2-16 は S2-1 の入力手段拡張。
- **CSV 列処理基盤**: S2-3 / A2-3 / B2-2 / B2-3 / B2-4 / B2-17 は「CSV 読込 → 列選択 → 処理 → CSV 出力」の同型構造。`papaparse` + Web Worker + 列選択 UI を共通コンポーネント化すると 2 本目以降の追加コストが激減する。
- **鍵・証明書系列**: A2-7 / B2-7 / 第1回 S-2 は PEM/DER パース基盤（`pkijs`）を共有するシリーズとして設計できる。
- **KDF**: セキュリティ視点の「KDF プレイグラウンド」案は A2-9 に統合（パラメータベンチ＋他言語相互運用チェックを内包）。
- **SAML**: バックエンド・セキュリティ両視点の案を S2-2 に統合。初版は「デコード＋構造表示＋定番チェックリスト」に絞り、XMLDSig 署名検証（C14N が山場）は第2版で検討。
- **検知器の実装規約**: S2-1 / A2-6 / B2-9 / B2-10 など「検出・警告」を持つツールは `.agents/rules/common.md` 3 章に従い **test-gates skill による陽性対照テストが必須**。

## 根拠資料（2026-11-03 確認）

- **[M1]** [MCP Security Best Practices: Local MCP Server Compromise](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#local-mcp-server-compromise) は、ローカルサーバの起動コマンド確認と同意・権限制限の必要性を説明する。設定表示を先に作る根拠とし、静的検査で実権限を判定できるとは解釈しない。
- **[M2]** [Claude Code の MCP 設定](https://code.claude.com/docs/en/mcp#environment-variable-expansion-in-mcp-json) は `mcpServers` と command / args / env / url / headers、変数参照を例示する。これはクライアントの設定形式であり、全 MCP クライアント共通規格ではない。
- **[E1]** [Promptfoo: Assertions & metrics](https://www.promptfoo.dev/docs/configuration/expected-outputs/) は、期待値との一致・構造・各種採点を区別する。比較時も異なる採点条件を混ぜない。
- **[E2]** [Promptfoo: export eval](https://www.promptfoo.dev/docs/usage/command-line/#promptfoo-export-eval-evalid) は JSON 出力と、export にプロンプト・出力・変数等の利用者データが残り得ることを説明する。ローカル閲覧の用途はあるが、需要規模は未調査。
- **[T1]** [OpenTelemetry GenAI semantic conventions](https://github.com/open-telemetry/semantic-conventions-genai) をトレース構造の参照元とする。対応版・エクスポート形式は実装時に明記する。規約の存在だけで全エージェント製品のログ互換性は主張しない。
- **[G1]** [GitHub Actions: Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use) は、最小権限・式に由来するスクリプト注入・特権 workflow の未信頼コード・依存固定を扱う。テキストから判定可能な部分だけを確認事項にする。
- **[D1]** [Chrome DevTools: HAR の保存](https://developer.chrome.com/docs/devtools/network/reference#save-as-har) は sanitized HAR で一部の認証ヘッダを除外する一方、機密情報付き export も提供する。既存サニタイズの有無を明示し、ログ・JSON を含むファイル横断の確認を追加価値とする。

## 重複・統合メモ（追加候補）

- `secret-scrubber`（S2-1）、`har-viewer`（S2-4）、`json-formatter` の PII マスク、`config-converter` の JSON Schema 検証は実装済み。S3-2 と A3-2 はこれらの検出資産を使う。既存の単体処理だけでは、形式をまたぐ同一値の採番状態は共有されない。

- 検知・マスキングは `test-gates` に従い、陽性対照と陰性対照を分ける。入力サイズ・深さ・件数制限、不正／未対応構造、安全なテキスト描画、strict CSP（eval・inline style なし）、入力由来の通信／保存がないことを受入条件に含める。
