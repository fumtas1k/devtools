# ツール技術リファレンス (`docs/tools.md`) 設計

作成日: 2026-05-30

## 目的

ツールが 20 個まで増えたため、各ツールが内部で**どう動くか**を開発者・コントリビュータ向けに解説するリファレンスを整備する。README のツール一覧（1 行説明）は「何ができるか」、本リファレンスは「どう動くか」を担い、住み分ける。

## 読み手・スコープ

- **読み手**: 開発者 / コントリビュータ（サイト利用者向けの使い方ガイドや SEO 目的ではない）
- **記載内容**: 各ツールにつき以下の 3 軸
  1. **仕組み・アルゴリズム** — 内部で何をしているか
  2. **準拠仕様・RFC・規格** — 該当規格へのリンクとこのツールでの解釈
  3. **制限・エッジケース** — 既知の制約・意図的な割り切り
- **書かないこと**: ライブラリ採用理由・代替案の比較（`docs/decisions.md` の担当領域。本リファレンスからはリンクで誘導する）

## 配置とリンク

- 新規ファイル `docs/tools.md` に全ツールを集約する（ツール単位の分割ファイルにはしない）。
- README の「## ツール一覧」冒頭に 1 行追加:
  `各ツールの技術的な仕組みは [docs/tools.md](docs/tools.md) を参照`
- 既存の README テーブル（カテゴリ別 1 行説明）はそのまま維持する。

## `docs/tools.md` の構造

```
# ツール技術リファレンス

（リードイン: 本ドキュメントの目的と decisions.md との住み分けを 2-3 行）

## 目次
- カテゴリ別にアンカーリンクを列挙

## 生成
### ULID生成
### UUID v7 生成
...

## コード・バーコード
...

## エンコード・デコード
...

## 変換・解析
...
```

- カテゴリ区切りは README と同一の 4 分類（生成 / コード・バーコード / エンコード・デコード / 変換・解析）。
- 各ツールは `### ツール名` 見出しの下に固定 3 小節（**仕組み・アルゴリズム** / **準拠仕様・RFC** / **制限・エッジケース**）を置く。
- 該当しない小節は省略してよい（例: ダミーテキスト生成に準拠 RFC は無い）。
- 冒頭に目次（カテゴリ別アンカー）を置き、ツール数増加に備える。

## 初期スコープ（本 PR で書く範囲）

構造（リードイン + 目次 + 全カテゴリ見出し + 全 20 ツールの見出し枠）を先に作り、**技術的に解説価値の高い代表 4 ツール**の本文を埋める。残りは見出し枠のみ用意し、後続 PR で段階的に埋める。

本 PR で本文を書く代表ツール:

1. **正規表現ビジュアライザ＆ReDoS検出** — 構造ツリー / 鉄道図の生成、壊滅的バックトラッキング検出のアルゴリズム、検出の限界
2. **QRチケット** — ECDSA 署名付与と公開鍵によるオフライン検証フロー、鍵の扱い、署名対象の範囲
3. **UUID v7 生成** — タイムスタンプ + ランダムフィールドのビット配置、RFC 9562、単調性の扱い
4. **TOTP/HOTP ジェネレータ** — RFC 6238 / RFC 4226 のコード生成・検証、シークレットがブラウザ外に出ない設計、時刻ずれ許容

各ツールの本文は実際のソース（`src/components/tools/` 配下と関連 `src/utils/`）を読んで正確に記述する。推測で書かない。

## ドリフト対策

`CLAUDE.md`（正本は `docs/shared-agent-rules.md` 4 章「ドキュメント更新ルール」）の表に行を追加:

| 変更の種類                                     | 更新が必要なファイル |
| :--------------------------------------------- | :------------------- |
| ツール追加・変更（技術解説に影響する挙動変更） | `docs/tools.md`      |

これにより、今後のツール変更時に解説の同期を促し、実装からの乖離を防ぐ。
