## [2026-04-27] lint-staged による partial-commit 安全な自動フォーマット

### 現象

従来の `.githooks/pre-commit` での Prettier 直接実行（`prettier --write <file> && git add <file>`）では、同一ファイル内の一部の変更のみをステージングしている場合（partial-commit）、未ステージの変更まで巻き込んでステージング・コミットされてしまう問題がありました。

### 教訓

**コミット時の自動フォーマットには `lint-staged` を使用すること。**

- `lint-staged` は内部で `git stash` 相当の処理を行い、未ステージの変更を一時的に退避してから整形・再 add を行うため、partial-commit のセマンティクスを壊しません。
- 拡張子ごとの処理ルールを `package.json` に集約できるため、シェルスクリプト側の複雑なループや抽出ロジックを排除でき、保守性が向上します。

## [2026-04-27] プルリクエスト作成時は明示的にベースブランチを指定する

### 現象

`gh pr create` をオプションなしで実行した際、リポジトリのデフォルト設定に従い `main` ブランチに向けてプルリクエストが作成されてしまいました。プロジェクトの運用では `develop` をベースにする必要があります。

### 教訓

**`gh pr create` を実行する際は、必ず `--base develop` を指定すること。**

### 予防策

プルリクエスト作成コマンドを以下のように徹底します：

```bash
gh pr create --base develop --title "..." --body "..."
```

## [2026-04-27] コミットメッセージの Conventional Commits 形式を強制する

### 背景

プロジェクト規約（`docs/shared-agent-rules.md`）で定められた「日本語かつ Conventional Commits 形式」が徹底されず、規約違反のコミットが混入するリスクがありました。

### 対策

`.githooks/commit-msg` フックを更新し、正規表現による形式チェックと日本語文字数チェックを組み合わせたバリデーションを導入しました。

### 教訓

**規約をドキュメントに書くだけでなく、Git Hook 等で自動的にガードすることで、エージェントや人間による不注意なミスを防ぐことができる。**

- **スキップ設定の重要性**: `Merge`, `Revert`, `fixup!`, `squash!` などの特殊なコミットは、Git 自身や外部ツールが自動生成することが多いため、チェック対象から外すことで開発フローの妨げを防ぎます。
- **わかりやすいエラーメッセージ**: 単にブロックするだけでなく、規約ドキュメントへのリンクや正しい例を提示することで、修正方法を即座に理解できるようにします。

## [2026-04-27] 実装開始前に必ず最新の develop からブランチを切る

### 現象

実装作業を古いブランチや誤ったベースブランチから開始してしまいました。また、ベースブランチ（`develop`）に切り替えた際に最新の状態を `git pull` することを失念していたため、リベース時に大規模なコンフリクトが発生するリスクがありました。

### 教訓

**新機能や修正の作業を開始する際は、必ず以下の手順を最初に行うこと。**

1. `git checkout develop` でベースブランチに移動します。
2. `git pull origin develop` で最新の状態を反映します。
3. `git checkout -b feat/<topic>` で新しいブランチを作成します。

もし誤ったブランチで作業を開始してしまった場合は、即座に `git stash` で変更を退避させ、上記手順で正しいブランチを作成してから `git stash pop` で変更を復元します。

## [2026-04-26] CopyButton の成功状態でラベル文字を固定する

### 現象

成功時テキストを「コピー」→「コピーしました」に切り替えていたため、ボタン幅が伸びて横並びレイアウト（Gs1Databar の GTIN-14 行など）が崩れました。

### 教訓

**コピーボタンの幅安定化のため、ラベル文字は idle / copied 両状態で固定すること。** 成功シグナルはアイコン swap（ClipboardIcon → CheckIcon）と色フリップ（`colors.success` / `colors.successBg`）のみで伝えます。

成功テキストを消すと今度はボタンが縮んで別のレイアウト崩れが起きます。GitHub・Stripe 等の確立された慣例でも「ラベルは変えず、アイコン + 色だけ変える」パターンが標準です。

### 副次改善

`aria-label` の動的 swap は `aria-live` への能動的通知に至らないため、`role="status" aria-live="polite"` の `sr-only` span に置き換えてスクリーンリーダー利用者にも成功を通知します。

## [2026-04-25] ホバー時の色変化はインラインスタイル＋`onMouseEnter`/`onMouseLeave` で

### 状況

`hover:bg-red-50` のような Tailwind ホバークラスが `Gs1Databar.tsx` / `JanCode.tsx` に残存し、規約の色クラス禁止に違反していました。

### 教訓

**ホバー切替は `onMouseEnter` / `onMouseLeave` でインラインスタイルを差し替える流儀に揃えること。**

```tsx
<button
  style={{ background: 'transparent', color: colors.error }}
  onMouseEnter={(e) => (e.currentTarget.style.background = colors.errorBg)}
  onMouseLeave={(e) => (e.currentTarget.style.background = 'transparent')}
>
  削除
</button>
```

## [2026-04-25] `Uint8Array<ArrayBuffer>` の戻り型は `crypto.subtle.verify` で必須

### 状況

`base64UrlToBytes(str): Uint8Array` と書くと TS は `Uint8Array<ArrayBufferLike>` に展開し、`crypto.subtle.verify()` の `BufferSource` 制約を満たせず型エラーになります。

### 教訓

**厳密な `BufferSource` を要求する API に渡す Uint8Array を返す関数は、戻り型を `Uint8Array<ArrayBuffer>` に絞り込むこと。**

## [2026-04-25] トグルの「意味の重さ」でリセット要否を分ける

### 現象

Base64 ツール等で、モード切替時に不必要に入力がリセットされたり、逆に保持されるべきでない場面で保持されたりしていました。

### 教訓

**トグルがもたらす「入力の意味の変化」の大きさで、リセット要否を判断すること。**

| トグルの種類                                  | リセット | 理由                         |
| :-------------------------------------------- | :------- | :--------------------------- |
| 操作の種類が変わる（エンコード/デコードなど） | する     | 入力の期待形式が変わるため。 |
| 同じ操作のサブバリアント（標準/URL-safeなど） | しない   | 出力比較のために保持が便利。 |

## [2026-04-25] `<label htmlFor>` がある場合は Select に aria-label を併用しない

### 状況

`<label htmlFor>` で紐付け済みの場合でも Select に `ariaLabel` を渡しており、冗長でした。

### 教訓

**`<label htmlFor>` で紐付け済みの場合、`aria-label` は付与しないこと（読み上げの優先順位により意図しない挙動になるのを防ぐため）。**
